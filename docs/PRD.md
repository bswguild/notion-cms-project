# PRD: 노션 레시피 웹/PDF 서비스 (MVP)

- 작성일: 2026-11-15
- 작성 대상: 1인 개발자 / 소규모 프로젝트
- 상태: Draft (MVP) — 기술 검증(prd-validator) 반영 완료 (2026-11-15)

## 1. 제품 목적/배경

Notion에 작성해 둔 요리 레시피를 별도의 CMS나 백엔드 개발 없이, 사용자가 보기 좋은 웹사이트에서 탐색하고 각 레시피를 PDF로 내려받을 수 있게 하는 서비스다. 콘텐츠 작성은 계속 Notion에서 하고(이미 익숙한 도구), 웹/PDF는 이 Next.js 프로젝트가 "읽기 전용 뷰어" 역할을 맡는다. 콘텐츠 관리용 어드민 UI를 새로 만들지 않아도 되는 것이 핵심 이점이다.

## 2. 타겟 사용자

- **콘텐츠 작성자(= 운영자 본인)**: Notion 데이터베이스에 레시피를 입력/수정하는 사람. 별도 로그인 없이 Notion에서 직접 작업.
- **방문자(웹 사용자)**: 레시피를 검색/탐색하고, 읽고, 필요하면 PDF로 저장해 인쇄하거나 오프라인으로 보는 일반 사용자. 로그인 불필요.

## 3. MVP 범위

### 포함 (MVP)

| ID | 기능 | 설명 |
|---|---|---|
| F001 | 레시피 목록 조회 | Notion DB에서 공개(`Published`) 레시피를 가져와 카드 목록으로 표시 |
| F002 | 카테고리/태그 필터링 | `Category`(단일 선택), `Tags`(다중 선택) 기준으로 목록 필터링 |
| F003 | 레시피 상세 조회 | 제목, 대표 이미지, 재료, 조리 순서, 조리시간/난이도/인분 등 표시 |
| F004 | 이미지 안정적 표시 | Notion 첨부 이미지의 임시 URL 만료 문제를 해결해 항상 이미지가 보이도록 처리 |
| F005 | PDF 다운로드 | 상세 페이지에서 해당 레시피를 PDF로 저장 |
| F006 | 빈 상태/에러 상태 표시 | 레시피 없음, Notion 연동 실패 시 사용자에게 안내 UI 제공 |
| F007 | Notion 데이터 캐싱 | 매 요청마다 Notion을 호출하지 않도록 캐싱, 일정 주기로 갱신 |
| F008 | 반응형 레이아웃 | 모바일/태블릿/데스크톱 대응 |
| F009 | 다크모드 대응 | 기존 프로젝트의 `next-themes` 다크모드와 통일된 스타일 |
| F010 | 레시피 상세 URL(Slug) | `/recipes/[slug]` 형태의 사람이 읽을 수 있는 경로 |
| F011 | 정렬(최신순) | 목록을 작성/게시일 기준 최신순으로 정렬 |

### 제외 (다음 버전 이후로 미룸)

- 사용자 로그인/회원가입, 즐겨찾기, 댓글, 평점
- 검색(키워드 전문 검색) — MVP는 카테고리/태그 필터로 대체
- 관리자 전용 어드민 UI (Notion 자체가 어드민 역할)
- 재료 기반 구조화 검색("이 재료로 만들 수 있는 요리")
- 서버 생성 고품질 PDF(`@react-pdf/renderer`) — MVP는 브라우저 인쇄 방식으로 시작
- 다국어 지원
- Notion 웹훅 기반 실시간 반영 — MVP는 시간 기반 캐시 갱신으로 충분

## 4. 주요 사용자 플로우

1. 방문자가 `/recipes`(레시피 목록)에 접속한다.
2. 카테고리/태그로 필터링해 원하는 레시피를 찾는다.
3. 레시피 카드를 클릭해 `/recipes/[slug]`(상세 페이지)로 이동한다.
4. 재료, 조리 순서, 대표 이미지를 확인한다.
5. "PDF로 다운로드" 버튼을 눌러 해당 레시피를 PDF로 저장한다(인쇄 다이얼로그를 통해 PDF로 저장, 또는 직접 인쇄).

운영자 플로우: Notion 데이터베이스에 레시피를 작성하고 `Published`를 체크하면, 캐시 갱신 주기(또는 수동 재검증) 이후 웹에 자동으로 반영된다. 별도 배포나 코드 수정이 필요 없다.

## 5. Notion 데이터 모델 / 연동 방식

### 5.1 Notion 구조상 주의점

2025-09-03 API 버전부터 하나의 Database 안에 여러 **Data Source**가 존재할 수 있는 구조로 바뀌었다. 구버전 예제의 `databases.query`가 아니라 **`dataSources.query`**를 사용해야 한다. `databases.retrieve`로 한 번 데이터소스 ID를 확인해 환경변수로 고정해 둔다.

> **구현 필수 조건**: `dataSources.query`는 `@notionhq/client` **v5.0.0 이상**에서만 제공된다. 또한 API 호출 시 `Notion-Version: 2025-09-03` 헤더(SDK의 `notionVersion` 옵션)를 명시해야 `databases.retrieve` 응답에 `data_sources` 배열이 포함된다. 이 저장소의 `package.json`에는 현재 `@notionhq/client`가 설치되어 있지 않으므로, 구현 착수 시 `v5+`로 신규 설치하고 버전을 고정한다.

### 5.2 인증/권한

- Notion Integration은 **Internal**, **Read content만** 권한으로 생성한다(쓰기 권한 불필요, 최소 권한 원칙).
- 레시피 데이터베이스 페이지에서 해당 Integration을 **Connection**으로 연결해야 API가 접근할 수 있다(연결하지 않으면 `object_not_found` 오류가 발생한다고 커뮤니티에서 폭넓게 보고됨 — Notion 공식 에러 레퍼런스에 명시된 사실은 아니므로 실제 구현 중 오류 메시지를 재확인한다). 권한은 Database 단위로 관리되므로, Database에 한 번 연결하면 그 안의 모든 Data Source에 함께 적용된다.

### 5.3 환경변수

- `.env.local`에 `NOTION_API_KEY`, `NOTION_RECIPES_DATA_SOURCE_ID`를 저장한다.
- `NEXT_PUBLIC_` 접두사를 붙이지 않는다(클라이언트 노출 금지). 서버 전용 모듈에서만 사용한다.

### 5.4 레시피 데이터베이스 속성 설계

| 속성 | 타입 | 용도 |
|---|---|---|
| `Name` | title | 레시피 제목 |
| `Slug` | rich_text | URL 경로용 고유 식별자 |
| `Published` | checkbox | 공개 여부 — 서버 쿼리에서 반드시 필터링해 초안을 숨김 |
| `PublishedAt` | date | 목록 정렬 기준 |
| `Category` | select | 한식/양식/중식/디저트 등 (단일) |
| `Tags` | multi_select | 간단, 비건 등 (다중) |
| `Difficulty` | select | 쉬움/보통/어려움 |
| `CookTime` | number | 조리 시간(분) |
| `Servings` | number | 인분 |
| `Cover` | files(**external 필수**) | 대표 이미지 |

> **중요**: `files` 속성에 Notion에 직접 업로드한 파일(`type: "file"`)을 쓰면 서명 URL이 약 1시간 후 만료된다(§6 이미지 처리 참고). 반면 `type: "external"`(외부 URL 참조)은 Notion 공식 문서상 만료되지 않는다("These links never expire and will always be returned as-is"). MVP에서는 `Cover`를 **external 타입으로만 운영하는 것을 기본 운영 규칙**으로 못박는다(예: 이미지 호스팅 서비스나 자체 스토리지에 올린 뒤 URL을 Notion에 붙여넣기).

재료와 조리 순서는 **Notion 본문 블록**(불릿/번호 리스트)으로 작성하는 것을 MVP 기본안으로 한다. 구조화된 재료 검색이 필요해지면 다음 버전에서 별도 속성(`MainIngredients` 등)을 추가로 검토한다.

### 5.5 데이터 조회/캐싱

- 목록은 `dataSources.query`의 filter(`Published` 등)/sorts로 조회하고, 100개가 넘을 경우 커서 기반 페이지네이션으로 전체를 수집한다.
- Rate limit(초당 약 3회)에 대비해 재시도 설정과 캐싱으로 호출 수 자체를 줄인다.
- 상세 페이지 본문은 블록 트리를 재귀 조회해 가져온다.

## 6. 기술 설계 방향 (이 저장소 아키텍처와의 연결)

- **신규 추가 요소**: 이 프로젝트에는 현재 `.env*`, API 라우트(`app/**/route.ts`), 미들웨어가 없다. 이번 기능을 위해 `.env.local`과 Route Handler를 새로 추가한다.
- **데이터 접근 계층**: `lib/notion/` 아래에 클라이언트, 환경변수 검증(zod), 속성 파서, 블록 트리 수집, 캐시된 도메인 함수(`getRecipes`, `getRecipeBySlug`)를 둔다.
- **캐싱 모델**: 이 프로젝트의 `next.config.ts`에 `cacheComponents: true`가 켜져 있으므로, 구버전 `revalidate` 방식이 아니라 **`"use cache"` + `cacheLife` + `cacheTag`** 모델을 사용한다. 콘텐츠 반영 주기는 30~45분 캐시를 기본으로 하고, 필요 시 시크릿으로 보호된 `/api/revalidate` 라우트로 온디맨드 갱신(`revalidateTag`)을 추가한다.
  - 기본 제공 `cacheLife` 프로필(`seconds`/`minutes`/`hours`/...)에는 "30~45분"에 정확히 맞는 것이 없으므로, `cacheLife({ stale, revalidate: 1800~2700, expire })` 형태의 **커스텀 프로필을 직접 정의**한다.
  - `revalidateTag`는 최신 API상 `revalidateTag(tag, cacheLife프로필명)` 형태로 두 번째 인자를 받을 수 있으므로, `/api/revalidate` 구현 시 이를 반영한다.
  - `"use cache"` 스코프 **내부에서는 `searchParams`/`cookies()`/`headers()`를 호출할 수 없다**. 따라서 카테고리/태그 필터 값을 캐시된 `getRecipes()` 안으로 그대로 넘기는 구조는 쓸 수 없다 — `getRecipes()`는 파라미터 없이 "공개된 전체 레시피 목록"만 캐시하고, 카테고리/태그 필터링은 캐시 바깥(클라이언트 또는 캐시된 결과를 받은 이후의 서버 레이어)에서 수행한다.
  - 신규 Route Handler(`/api/revalidate`, 이미지 프록시 등)에는 레거시 라우트 세그먼트 설정(`export const dynamic`/`revalidate`/`fetchCache`)을 쓰지 않는다 — `cacheComponents: true`와 함께 쓰면 빌드 에러가 발생한다.
  - 서버리스 배포(예: Vercel) 환경에서는 메모리 캐시 항목이 재검증 사이에 유지되지 않고 콜드스타트마다 리셋될 수 있다는 점이 Next.js 공식 문서에 명시되어 있다. 배포 타깃을 먼저 확정하고, 서버리스라면 "30~45분 캐시로 Notion 호출을 줄인다"는 전제가 기대만큼 효과적이지 않을 수 있음을 감안한다.
- **이미지 처리**: Notion에 직접 업로드한 파일(`type: "file"`)의 서명 URL은 약 1시간 후 만료된다. 캐시된 페이지에 그대로 쓰면 이미지가 깨지므로, **MVP 기본안은 §5.4에서 명시한 대로 `Cover`를 external 타입으로만 운영**해 만료 문제 자체를 피한다(공식 문서상 external URL은 만료되지 않음). 운영자가 Notion에 직접 업로드한 이미지를 쓰고 싶어 하는 경우를 대비한 폴백으로 이미지 프록시 Route Handler(`app/api/recipe-image/route.ts`)를 둘 수 있으나, **이 프록시는 "고정 URL로 단순 중계"가 아니라 요청이 들어올 때마다 Notion API를 다시 호출해 최신 서명 URL을 재조회한 뒤 스트리밍/리다이렉트하는 동적 엔드포인트로 설계해야 한다** — 캐시되는 대상은 "어떤 블록/파일을 가져올지"일 뿐, 서명 URL 값 자체를 캐시하거나 페이지에 박아두면 안 된다.
- **컴포넌트 계층**: 기존 `ui → common → layout → sections` 계층을 따른다. 레시피 전용 블록은 `components/sections/recipes/*`(카드, 필터 바, 상세 섹션)에 둔다. Notion 블록 렌더러처럼 범용적인 부품은 `components/common/`에 둔다.
- **상태 관리**: 카테고리/태그 필터 UI 상태는 Zustand 스토어로 관리하고, URL 쿼리스트링과 동기화한다. 이 저장소의 `package.json`에는 `zustand`가 아직 설치되어 있지 않으므로 구현 착수 시 신규 설치가 필요하다. 필터 UI에 다중 선택 태그 컴포넌트가 필요한데, `base-nova`(Base UI 기반) shadcn 레지스트리에 기본 제공되는지는 구현 전 `shadcn` MCP로 먼저 확인한다.
- **폼 검증**: 이 MVP는 사용자 입력 폼이 거의 없지만(필터 UI 정도), 필요하다면 `react-hook-form` + `zod` 패턴을 그대로 따른다.
- **타입 안전성**: Notion API 응답은 discriminated union 구조이므로, `any`를 쓰지 않고 타입가드 함수로 속성을 파싱한 뒤, zod 스키마로 도메인 타입(`RecipeSummary`, `RecipeDetail`)을 검증한다.
- **PDF 다운로드 구현**: MVP 1차는 **`window.print()` + `@media print` 전용 스타일**로 구현한다. 서버 렌더링 비용과 한글 폰트 등록 문제를 피할 수 있어 가장 빠르게 구현 가능하다. 향후 더 통일된 PDF 품질이 필요해지면 `@react-pdf/renderer`(서버 생성, 한글 폰트 직접 등록 필요) 방식으로 고도화하는 것을 옵션으로 남겨둔다.

## 7. 비기능 요구사항

- **반응형**: 모바일 우선으로 목록/상세 레이아웃을 구성하며, 모든 화면 크기에서 깨지지 않아야 한다.
- **다크모드**: 기존 `ThemeProvider`(class 전략)와 통일된 `dark:` variant 스타일을 적용한다.
- **성능**: 레시피 목록/상세는 캐시된 데이터로 빠르게 응답해야 하며, 사용자 요청마다 Notion API를 직접 호출하지 않는다.
- **안정성**: Notion API 장애나 속성 값 누락 시에도 사이트 전체가 깨지지 않아야 한다(행 단위 검증 실패는 건너뛰고 로그만 남김).
- **보안**: Notion API 키는 서버 전용으로만 사용하며 클라이언트에 노출되지 않는다.

## 8. 성공 지표

- 운영자가 Notion에 레시피를 추가/수정한 뒤, 코드 수정 없이 웹사이트에 반영되는 것을 확인할 수 있다.
- 방문자가 레시피 상세 페이지에서 PDF 다운로드(인쇄)를 완료할 수 있다.
- 모바일/데스크톱에서 레이아웃이 깨지지 않는다.
- Notion 이미지가 시간이 지나도(캐시 만료 전/후 모두) 깨지지 않고 표시된다.

|---|---|---|
| 이미지 URL 만료 | Notion 첨부 이미지 서명 URL이 약 1시간 후 만료되어 캐시된 페이지에서 이미지가 깨질 수 있음 | 이미지 프록시 라우트 또는 external URL 운영 |
| Notion API Rate Limit | 초당 약 3회 제한, 레시피가 많아지면 전체 수집 시 영향 가능 | 캐싱, 동시성 제한, 재시도 전략 |
| PDF 충실도 | `window.print()` 방식은 브라우저별 인쇄 스타일 차이가 있을 수 있음 | MVP는 허용, 품질이 중요해지면 서버 생성 방식으로 전환 |
| Notion 스키마 변경 취약성 | 속성 이름을 Notion에서 바꾸면 코드가 조용히 깨질 수 있음 | 속성 이름 상수화, zod 검증 실패 로깅 |
| Database/Data Source API 변경 | 최근 API 변경사항(2025-09-03)에 대한 이해가 필요 | `dataSources.query` 기준으로 구현, `@notionhq/client` **v5.0.0 이상** 설치 + `Notion-Version: 2025-09-03` 헤더 고정 |
| 캐싱-필터 상호작용 | `"use cache"` 스코프 내부에서 `searchParams`를 쓸 수 없어, 캐시된 함수에 필터 값을 그대로 넘기는 구조는 동작하지 않음 | `getRecipes()`는 전체 목록만 캐시, 카테고리/태그 필터링은 캐시 바깥 레이어에서 수행 |
| 캐시 지속성(서버리스) | 서버리스 배포 시 메모리 캐시가 재검증 사이에 유지되지 않아 "30~45분 캐시로 호출 감소" 전제가 흔들릴 수 있음 | 배포 타깃을 먼저 확정하고, 서버리스라면 추가 완화책(동시성 제한 등) 검토 |
| 미설치 의존성 | `@notionhq/client`, `zustand`가 현재 `package.json`에 없음 — 설계상 "그대로 따른다"는 서술이 신규 설치 필요성을 가릴 수 있음 | 구현 착수 전 의존성 설치 계획을 기술 설계 섹션에 명시 |
